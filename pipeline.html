Connector pipeline

From request to published connector: who acts, which artifact each step needs and makes, and what is passed on at every handoff.

You Claude Colleague Needs an input artifact Makes an output artifact Gap not decided yet
1

Request arrives

You

Needs

  • A customer request

Makes

  • Azure DevOps ticket: customer name, link to the API documentation, what the customer wants
Sign-off: none. The customer's wishes are adjusted as the last step.
Handoff 1: request to API research
Passed on
Customer name, API documentation link, what the customer wants
Used by
Claude's API research
Lives in
Azure DevOps ticket
2

Give Claude the API specification

You

Needs

  • API specification: JSON, YAML, Word or PDF
  • The connector name

Makes

  • Path or link given in the session
  • The spec stays outside the repo, wherever you keep it
Sign-off: none. Never add the spec to the repo.
3

Ask the vendor or customer

Claude draftsYou send

Needs

  • An unclear spec (this happens in almost every API)

Makes

  • Email questions and answers, in your mailbox
  • Sometimes a note in the ticket
Sign-off: you approve each email. Waits run from days to weeks. You either stop work or build on assumptions, and fix any gap later.
4

Write the API research report

Claude

Needs

  • The API specification
  • Vendor and customer answers, as you tell them

Makes

  • Research report: capabilities, caveats, which of create, enable, disable, update and delete are supported
  • reports/<Name>-feasibility.md, local, ignored by git
Sign-off: you sign off before the connector is built from it.
Handoff 2: research to development
Passed on
The signed-off report
Used by
Writing the code
Lives in
harness\reports\<Name>-feasibility.md, your machine only. The emails stay in your mailbox.
5

Create the branch and the connector folder

Claude

Needs

  • Your instruction to build, with the connector name
  • Template: the target folder of the Tools4ever V2 template repo
  • A first commit on main, made by you

Makes

  • Branch <Name> in the harness repo
  • Folder Generated\<Name> filled with the template files
Sign-off: none. Claude may push task branches only, never main.
6

Develop the connector

Claude

Needs

  • The template files in Generated\<Name>
  • The signed-off report

Makes

  • Connector code: the five action scripts, import.ps1, fieldMapping.json, configuration.json
  • README with a Remarks section for caveats, and CHANGELOG
Sign-off: you sign off the code, README and CHANGELOG before they go into the pull request. Everything in the README is published.
Handoff 3: development to testing
Passed on
The code, the credentials, the connection settings, and a mock if needed
Used by
Testing
Lives in
Code on the branch. Credentials and connection settings in KeePassXC, which Claude never reads. The mock on your machine.
7

Test

YouClaude, mocks only

Needs

  • Production, a vendor test environment, or a mock, depending on what is available
  • KeePassXC entries: credentials and connection settings

Makes

  • Mock of the API, when no real environment exists
  • test folder: debug scripts and actionContext.json, local, ignored by git
Sign-off: none for the mock and the test folder. Claude only tests against mocks and never uses the KeePassXC CLI. Waiting for test access also takes days to weeks.
Handoff 4: testing to review
Passed on
The code in a pull request. Caveats are in the README's Remarks section, and the pull request description only points to it.
Used by
Your colleague
Lives in
Azure DevOps pull request
Gap: harness branch to Azure DevOps
Problem
The code now lives on a harness branch on GitHub, but the review is a pull request in Azure DevOps. How the code moves from one to the other is not decided.
8

Review

You open itColleague reviews

Needs

  • The code, README and CHANGELOG

Makes

  • Pull request in Azure DevOps with code comments
  • Usually one round of changes
Sign-off: your colleague's review. You create the pull request and its description yourself.
Handoff 5: approved review to publishing
Passed on
Everything in the connector folder except the test folder, including README and CHANGELOG
Used by
The published connector
Lives in
GitHub repo, added by hand
9

Publish

You

Needs

  • The approved connector files
  • The connector name

Makes

  • GitHub repo HelloID-Conn-Prov-Target-<Name>, created by hand
Sign-off: you produce it yourself. Claude doesn't prepare or decide the publication. Nothing follows this step.

Standing artifacts

Needed throughout

  • CLAUDE.md: the harness agreement Claude reads each session
  • systems.md: workflow, systems and handoffs

Yours alone

  • Best-practices file in C:\_Data\connector-shared. Claude doesn't change it.

Source for new connectors

  • Tools4ever V2 template on GitHub, the target folder

Gaps

  • The route from the harness branch to the Azure DevOps pull request is not decided.
  • One line in systems.md still says you develop the code "in Azure DevOps". That is out of date next to steps 5 and 6.
Built from the decisions in CLAUDE.md and systems.md. Local files only: reports, test folders and the API spec are never committed.
